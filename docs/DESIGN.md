# 단계별 설계 (Phase 1 → 5)

## 자동화 가능성 결론

**가능합니다.** 실제로 이 저장소에서 Phase 1 전 구간을 구현하고 1080x1920 mp4 출력까지
확인했습니다. 다만 파이프라인을 **기계적 작업**과 **판단이 필요한 작업**으로 나눠서 봐야 합니다.

| 구간 | 성격 | 자동화 수준 |
| --- | --- | --- |
| 얼굴 감지·블러 | 기계적 (모델 추론) | 완전 자동. 단 재현율 100%는 불가 → 사람 검수 필요 |
| 켄 번즈·컷·자막 애니메이션 | 기계적 (규칙) | 완전 자동 |
| BGM 합성 | 기계적 (신호 처리) | 완전 자동. 저작권 문제 없음 |
| 렌더링 | 기계적 (ffmpeg) | 완전 자동 |
| 활동 내용 해석 | 판단 | Claude 멀티모달 필요 (Phase 2) |
| 카피·자막 문구 | 판단 | Claude 필요. 사실관계는 사람 검수 권장 |
| 유튜브 게시 | 정책·책임 | API 자동화 가능하나 사람 승인 단계 유지 권장 |

즉 **"사진만 넣으면 영상이 나온다"는 이미 동작**하고, **"사진만 넣으면 유튜브에 올라간다"는
기술적으로 가능하지만 권장하지 않습니다.** 학생 얼굴이 들어간 콘텐츠라 블러 누락 한 건의
비용이 너무 큽니다.

## Phase 1 — MVP ✅ 구현 완료

**목표**: 폴더 경로와 설명 한 줄을 넣으면 9:16 mp4 가 나온다.

**구성**

| 모듈 | 역할 |
| --- | --- |
| `shorts_pipeline/face_blur.py` | 얼굴 감지(MediaPipe/YuNet/Haar) + 타원 모자이크 + 검수 시트 |
| `shorts_pipeline/head_detect.py` | 사람 검출 + 자세 추정으로 머리 영역 찾기 (기본 감지 경로) |
| `shorts_pipeline/captions.py` | 제목·장면별 자막 계획 (`CaptionPlan`) |
| `shorts_pipeline/kenburns.py` | 켄 번즈 확대·이동, 블러 배경으로 9:16 채우기 |
| `shorts_pipeline/subtitles.py` | 한글 자막을 RGBA 이미지로 렌더링 |
| `shorts_pipeline/bgm.py` | 코드 진행 기반 BGM 자체 합성 |
| `shorts_pipeline/render.py` | 장면 합성·크로스페이드·자막 애니메이션·mp4 출력 |
| `shorts_pipeline/pipeline.py` | 전 구간 오케스트레이션 + 실행 리포트 |

**검증 결과**

| 항목 | 값 |
| --- | --- |
| 출력 규격 | 1080x1920, 30fps, H.264 High, yuv420p, AAC 스테레오 |
| 렌더링 시간 | 사진 5장 18초 영상 기준 약 125초 (`--preview` 는 약 15초) |
| 감지 (실제 교실 사진) | 사람 45명 중 43명 (사람 검출 + 자세 추정) |
| 감지 (얼굴 전용 비교) | 사람 45명 중 13명 |
| 테스트 | 55개 통과 (빠른 49개 + 렌더링 포함 6개) |

**설계 판단**

- **검수 시트를 필수 산출물로 만들었습니다.** 블러 누락은 자동으로 알 수 없으므로,
  무엇을 가렸는지 한 장으로 보여주는 것이 유일하게 믿을 수 있는 안전장치입니다.
- **모자이크 칸을 일부러 크게 잡았습니다.** 얼굴 영역을 가로·세로 5칸으로 나눕니다.
  칸이 작으면 이목구비가 남아 재식별 위험이 생깁니다.
- **과잉 차단을 감수합니다.** 얼굴이 아닌 곳이 가려지면 보기에 아쉬울 뿐이지만,
  놓치면 개인정보 노출입니다. 두 오류의 비용이 전혀 달라서 한쪽으로 치우쳐 설계했습니다.
- **BGM 을 직접 합성합니다.** 외부 음원을 받지 않으므로 저작권 검토가 아예 불필요합니다.

### 실제 교실 사진으로 검증하며 설계가 한 번 바뀌었습니다

합성 테스트 사진에서는 MediaPipe 얼굴 감지가 14/14 로 완벽했습니다. 그런데 실제
교실 사진 5장(사람 45명)에 적용하자 **13명밖에 찾지 못했습니다.**

원인은 얼굴 감지기의 본질적 한계였습니다. BlazeFace 계열은 정면을 향한 얼굴을 찾도록
학습돼 있는데, 교실에서 학생들은 고개를 숙이고 필기하거나, 옆 친구를 보거나, 카메라에
등을 지고 앉아 있습니다. 확률 임계값을 0.5 에서 0.1 까지 낮추고 해상도를 원본까지
올려도 결과가 **전혀 바뀌지 않았습니다.** 모델이 애초에 후보로 올리지 못한 것입니다.

그래서 감지 대상을 '얼굴'에서 '머리'로 바꿨습니다.

| 신호 | 역할 |
| --- | --- |
| 얼굴 감지 (전체 + 타일 분할 확대) | 잡히면 가장 정확한 경계 |
| 사람 검출(YOLO) → 사람별 자세 추정 | 코·눈·귀 랜드마크로 머리 위치 추정. 얼굴이 안 보여도 동작 |
| 사람 박스 상단 기하 추정 | 위 둘이 모두 실패했을 때의 대비책 |

세 결과를 합집합으로 합칩니다. 결과는 45명 중 43명입니다.

| 방식 | 찾은 사람 |
| --- | --- |
| 사람 검출 + 자세 추정 | 43 / 45 |
| 얼굴 감지만 | 13 / 45 |

**여기서 배운 것**: 합성 데이터로 검증한 성능은 실제 데이터에서 그대로 재현되지
않습니다. 특히 개인정보가 걸린 기능은 반드시 실제 데이터로 확인해야 합니다.

**남은 한계**: 43/45 는 자동 게시를 맡길 수 있는 수치가 아닙니다. 사진 가장자리에서
몸이 크게 잘렸거나 다른 사람에 거의 가려진 사람은 여전히 놓칩니다. 검수 시트 확인과
`--faces-json` 보완은 선택이 아니라 필수 단계입니다.

## Phase 2 — 자동 카피·자막

**목표**: 매번 같은 템플릿 문구가 아니라, 사진 내용에 맞는 자막이 나온다.

**연결 지점은 이미 열려 있습니다.** `CaptionPlan`(제목 + 장면별 자막 + 해시태그)이
자막 생성과 렌더링 사이의 계약입니다. Phase 1 은 `TemplateCaptionGenerator` 가 채우고,
Phase 2 는 같은 자리를 Claude 가 채웁니다.

**지금 바로 수동으로 쓰는 법**

```bash
python scripts/make_caption_prompt.py ./photos/과학실험 -d "화산 폭발 실험" > prompt.txt
# prompt.txt 와 사진을 Claude 에 함께 전달 → 받은 JSON 을 captions.json 으로 저장
python make_shorts.py ./photos/과학실험 -d "..." --captions captions.json
```

**자동화할 때 할 일**

1. `captions.py` 에 `ClaudeCaptionGenerator` 추가. `CaptionGenerator` 프로토콜만 지키면 됩니다.
2. 블러 처리된 사진을 base64 로 인코딩해 Messages API 에 첨부. 원본이 아니라 **블러 후**
   이미지를 보내는 것이 중요합니다.
3. 응답 JSON 을 `CaptionPlan` 으로 파싱하고, 실패하면 템플릿 생성기로 안전하게 대체.
4. 개인정보 금지 규칙(학교·학년·이름)은 프롬프트와 후처리 양쪽에서 검사.

**주의**: 생성된 문구의 사실관계는 사람이 한 번 읽어야 합니다. 사진만 보고 "화산 실험"을
"화학 실험"으로 쓰는 식의 오류가 나올 수 있습니다.

## Phase 3 — 활동 유형별 템플릿

**목표**: 영상 패턴이 매번 똑같지 않게 한다.

**확장 지점**: `bgm.py` 의 `STYLES` 딕셔너리와 `config.py` 의 `ShortsConfig`.

| 활동 유형 | BGM | 편집 성격 |
| --- | --- | --- |
| 과학실험·만들기 | `bright` | 중간 속도, 확대 위주 |
| 체육대회·발표회 | `energetic` | 빠른 컷, 큰 확대폭 |
| 미술·독서·현장학습 | `calm` | 느린 이동, 긴 장면 |

할 일: `TemplatePreset` 데이터클래스를 만들어 BGM 스타일·장면 길이·확대폭·자막 위치를
하나로 묶고, Phase 2 의 Claude 응답에 `activity_type` 필드를 추가해 자동 선택합니다.

## Phase 4 — 폴더 감시 자동 실행

**목표**: 사진만 올리면 명령어 없이 진행된다.

설계:

1. `watchdog` 으로 지정 폴더를 감시합니다.
2. 새 파일이 생긴 뒤 **조용해질 때까지 기다립니다**(디바운스 2~3분). 사진을 여러 장
   복사하는 중에 실행되면 일부만 들어간 영상이 나옵니다.
3. 하위 폴더 하나를 한 건으로 묶어 `run_pipeline` 을 호출합니다. 폴더명을 활동 설명의
   기본값으로 씁니다.
4. 결과를 `output/` 에 저장하고, **검수 대기 상태로 둡니다**. 자동 게시는 하지 않습니다.
5. 실패하면 재시도하지 말고 로그를 남깁니다. 같은 사진으로 반복 실패할 가능성이 큽니다.

주의: 동시 실행 방지를 위한 잠금 파일이 필요합니다. 렌더링이 CPU 를 오래 점유합니다.

## Phase 5 (선택) — 유튜브 업로드

**목표**: 게시까지 연결하되, 사람 승인은 유지한다.

설계:

1. YouTube Data API v3, OAuth 2.0 (`youtube.upload` 스코프). 리프레시 토큰을 안전하게 보관.
2. **비공개(private)로 업로드**하고, 사람이 검수 후 직접 공개로 바꿉니다. 이 한 단계가
   블러 누락·자막 오류에 대한 마지막 방어선입니다.
3. 제목·설명·해시태그는 `captions.json` 에서 가져옵니다.
4. 일일 업로드 할당량(기본 프로젝트는 하루 6건 수준)을 초과하면 대기열에 넣습니다.
5. 아동이 등장하는 콘텐츠의 시청자 설정(made for kids)과 학교 정책을 확인합니다.

## 권장 진행 순서

1. **근접 사진 위주로 5~8장을 고르세요.** 얼굴이 크게 나오는 사진일수록 감지가 잘 되고
   숏폼 화면에서도 잘 보입니다. 교실 전체를 멀리서 담은 사진은 양쪽 모두 불리합니다.
2. `review_sheet.jpg` 에서 놓친 얼굴이 있는지 확인하고, 있으면 `--faces-json` 으로 보완합니다.
3. 결과물이 쓸 만하면 Phase 2 를 수동 프롬프트로 먼저 써 보고, 문구 품질이 만족스러울 때
   API 자동화로 넘어가세요.
4. 품질이 안정된 뒤에 Phase 3·4 로 확장하고, Phase 5 는 마지막에 검토하세요.
